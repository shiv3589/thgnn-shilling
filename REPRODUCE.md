# Reproducibility Guide

This document covers environment setup, data download, expected runtimes, and output validation for the TH-GNN paper experiments.

---

## 1. Environment setup

**Requirements:** Python 3.9+, 16 GB RAM, ≥ 20 GB free disk. A CUDA GPU speeds up Stages 1 and 3 significantly but is not required.

```bash
# 1. Clone and enter the repository
git clone <repo-url> thgnn-shilling
cd thgnn-shilling

# 2. Create a virtual environment (conda or venv)
conda create -n thgnn python=3.10 -y && conda activate thgnn
# OR
python3 -m venv .venv && source .venv/bin/activate

# 3. Install PyTorch (match your CUDA version — see pytorch.org)
#    CPU-only example:
pip install torch torchvision --index-url https://download.pytorch.org/whl/cpu
#    CUDA 12.1 example:
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu121

# 4. Install torch-geometric and all other dependencies
pip install torch-geometric
pip install -r requirements.txt
pip install -e .          # editable install of the src/ package

# 5. Verify the install
python -c "import src.models; print('OK')"
```

## 3. Running the full pipeline

Run the single entry-point script from the repository root:

```bash
bash scripts/reproduce_paper.sh
```

To parallelise across 4 CPU cores or use a GPU:

```bash
WORKERS=4 DEVICE=cuda bash scripts/reproduce_paper.sh
```

If embeddings were already pre-computed (e.g. resuming after Stage 1):

```bash
SKIP_EMBED=1 bash scripts/reproduce_paper.sh
```

All intermediate and final outputs are written under `results/`.

---

## 4. Expected runtime per stage

GPU timings measured on a single A100 (80 GB) with `WORKERS=4`. CPU-only timings estimated on a 16-core machine (Intel Xeon, ~10–12× slower per experiment than A100).

| Stage | Description | GPU (A100) | CPU-only (16-core) |
|---|---|---|---|
| 0 | Sanity checks | < 1 min | < 1 min |
| 1 | Pre-compute RoBERTa embeddings (all 4 datasets) | ~45 min | ~7 h |
| 2 | LightGCN clean baselines (all 4 datasets) | ~20 min | ~3 h |
| 3 | Full 720-experiment matrix | ~18 h | **not feasible** ¹ |
| 4 | Ablation study (240 experiments) | ~6 h | ~3 days ² |
| 5 | Aggregate → tables | < 5 min | < 5 min |
| 6 | Analysis figures (notebook) | ~30 min | ~4 h |

¹ Stage 3 on CPU (~8 days wall-clock) is impractical for a single machine. **Run on a GPU machine.** On CPU, use `--dry-run` (ml1m × random, 2 seeds) or restrict with `--dataset ml1m --attack random` to verify the pipeline end-to-end.

² Stage 4 is CPU-feasible only with `WORKERS=8` or higher; expect 2–3 days.

**Stage 3 tips for managing runtime:**

- Use `WORKERS=4` (GPU) or higher if enough RAM is available (≥ 4 GB per worker).
- The script resumes automatically: re-running skips already-completed experiment files.
- To run a subset, pass flags directly to `run_experiments.py`:
  ```bash
  python scripts/run_experiments.py --dataset ml1m --attack random --workers 4
  ```

## 6. Validating results against paper numbers

### 6a. Automatic check (recommended)

```bash
python -m pytest tests/test_reproducibility.py -v
```

This runs a 5 %-subsample of the pipeline (one dataset, one attack, one seed) and checks that F1 scores are within ±0.03 of the expected values recorded in `configs/paper_runs.yaml`.

The full-data check requires completed results in `results/raw/`:

```bash
python -m pytest tests/test_reproducibility.py -v -m full
```

### 6b. Manual checksum verification

After a full run, verify table integrity against the published manifest:

```bash
# Generate checksums from your run
shasum -a 256 results/tables/*.csv results/lightgcn_clean.json \
    > results/my_checksums.sha256

# Diff against the published manifest (stored in configs/paper_runs.yaml
# under output_checksums once populated after the reference run)
diff results/checksums.sha256 results/my_checksums.sha256
```

To verify the code is importable and core logic is correct without downloading data:

```bash

```

To run the fast reproducibility smoke test on synthetic data:

```bash

```

## 8. Troubleshooting

### Known install issues

> **setuptools < 69.1.0:** if `pip install -e .` fails with a missing `setuptools.backends.legacy` error, this is fixed in the current `pyproject.toml`. If you still see it, run `pip install --upgrade setuptools` first.

### General troubleshooting

| Problem | Solution |
|---|---|
| `FileNotFoundError` in Stage 1 | Check `data/raw/<dataset>/` exists and files match the layout in §2 |
| CUDA out of memory | Reduce `--batch-size` or use `DEVICE=cpu` |
| Stage 3 running for days on CPU | Use `WORKERS=4` and/or restrict to `--dataset ml1m --attack random` for a quick smoke check |
| `ModuleNotFoundError: src` | Run `pip install -e .` from the repo root |
| Notebook execution fails in Stage 6 | `pip install nbconvert ipykernel` and re-run |
| F1 differs by > 0.03 from paper numbers | Check that `--seed` matches, that `splits.strategy: temporal` is active, and that embedding cache is not stale (delete `data/processed/` and re-run Stage 1) |
